# Response to the 2026-08-24 design review

**Reviewed document:** [2026-08-24-codex-design-review.md](2026-08-24-codex-design-review.md)
**日本語版:** [2026-08-24-codex-design-review.ja.md](2026-08-24-codex-design-review.ja.md)

The review's central finding was correct and worth stating plainly: the privacy
guarantee failed open. Names and addresses escaped when Gemma was unavailable, a
failed leak check did not stop a release, caller-controlled placeholders formed a
rehydration oracle, and rehydrated PII was persisted indefinitely outside the
TTL-protected vault. Each of those is now closed.

The rest of this document records what changed, and — as importantly — what we
decided not to do and why.

## The governing decision: cut scope, then fail closed

The review offered a choice on the vault: fix concurrency and expiry properly
(8–12 h), or cut shared sessions (2–3 h). We cut, and cut further than asked.

There is now **one server-generated request id per request**, minted by the
gateway as a UUIDv7 and used as the vault key. `POST /v1/ask` accepts only
`{text}`. A body carrying `session_id` is rejected with 400 rather than silently
ignored, because a caller who believes they chose a vault key and did not is worse
off than one told plainly they cannot. The inbound `X-Request-ID` header is
**ignored entirely**: the gateway returns its own id in the response header, so a
caller reading it back gets the server's id, not its own. Nothing echoes the
inbound value. It is the vault key, and a caller who could choose it could name
another request's mapping.

That single change removes the cross-session oracle, the concurrency race, the
expiry-restart collision, and the multi-turn linkage risk at once. Placeholder
stability across turns is gone with it; that is a real capability loss, and the
right trade for a submission.

## §2 — trust-boundary weaknesses

| Weakness                                                  | What we did                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| --------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Gemma span extraction fails open**                      | Extraction now returns a discriminated `valid-empty \| valid-spans \| invalid`. An empty list is only believed when the model actually said `{"spans": []}`; a malformed, fenced-but-broken, or argued-away answer is `invalid` and the request returns 502 without ever reaching Core. Temperature is 0, untrusted input is wrapped in `<<<INPUT … INPUT>>>` delimiters that are stripped from the input first, and the instruction states that the delimited text is data and never a command. The UI can no longer show "PASS" and "Gemma flagged" together, because a flag means there is no answer to show.                                                                                                                                                                                                 |

## Human approval: removed, and why

The review's suggestion was "remove, or derive the reviewer from verified
IAP/OIDC claims". We removed it — the routes, the UI button, the config key, the
client command, the tests and the documentation.

The reason is worth recording, because it is not "we ran out of time". The public
gateway authenticates nobody. There is no principal to name, so a `human:<id>`
actor minted from a click is a claim about a person who was never identified —
and under OKF §5.3 that claim is exactly what raises a document to
_human-reviewed_. Emitting it would not be a weak signal; it would be a false one,
and it would devalue the tier for every consumer that reads the document.

The trust-tier derivation itself stays generic in `packages/common/src/okf.ts`.
OKF is a general format and other consumers do have authenticated reviewers. This
product simply never mints a `human:` actor, and the UI reports **review identity:
none**, always, as one of four separate dimensions rather than as an absence the
reader has to infer.

## §3 — OKF v0.2

Every material defect the review listed is addressed.

1. **Generator attribution.** `generated.by` is now `synthesis_agent/<version>`.
   Synthesis assembles the concept; §7 attributes a document to whoever wrote it.
2. **Core as provenance.** The Core invocation is a `sources[]` entry —
   `core-response`, `resource: /requests/<id>/core-response.md`,
   `author: core_agent/<GEMINI_MODEL>` — alongside `masked-prompt` and
   `pii-policy`.
3. **Verifier attribution.** `verified[].by` is
   `process:leak-check@<attester sha256 short>`. TypeScript regex code decides the
   verdict; Gemma only ever advises, so naming a Gemma model as the verifier was
   simply wrong. The body now says "leak-policy check", not "verified", and states
   that it is not a factual validation of the answer.
4. **Provenance no longer dangles.** `/v1/requests/:id/masked-prompt.md` and
   `/v1/requests/:id/core-response.md` are real routes serving the stored masked
   artifacts, and `GET /v1/requests/:id` serves the evidence document itself.
5. **The attester resolves.** `knowledge/references/attesters/leak_check.ts` is a
   byte-identical copy of the module Synthesis imports, and
   `packages/common/test/attester_bundle.test.ts` fails if their SHA-256 digests
   diverge. A judge can follow `attester.resource` and run the file; a reader can
   confirm from `attestation.attester_sha256` which bytes produced their verdict.
   We chose copy-plus-test over a `paths` mapping because TypeScript's `rootDir`
   will not compile a source file from outside the package tree, and a bundle
   whose sanctioned attester cannot be executed is not attestable.
6. **The receipt contract is complete.** `executor.receipt` and what `verify()`
   demands are now the same five fields — `request_id`, `masked_prompt_hash`,
   `response_hash`, `findings`, `response` — exported from the attester as
   `RECEIPT_FIELDS` and asserted equal in a test. `masked_prompt_hash` is new: it
   binds a verdict to the exact exchange that produced it, so a receipt cannot be
   replayed as evidence for another.
7. **Machine-readable evidence is persisted.** A top-level `attestation:` block
   carries `computation`, `computation_sha256`, `attester_sha256`,
   `masked_prompt_sha256`, `core_response_sha256`, `verdict`, `checked_at`,
   `request_id`, `trace_id` and `withheld`.
8. **Malformed trust metadata fails closed.** A `verified` entry without a string
   `by` names nobody and no longer votes, so `verified: [{}]` derives
   _unverified_. An absent or unparseable `stale_after` derives freshness
   `unknown`, never `fresh`; `isStale()` treats `unknown` as stale so a caller
   asking the yes/no question fails closed. The malformed value itself is still
   preserved in the document (§11).
9. **"Signed" is gone.** There is no signature and no MAC, so the word does not
   appear. A test asserts it never reappears in a generated document. Same for
   "append-only" (the record is a per-request document with a TTL), "never leaks",
   and "all PII".
10. **Bundle drift fixed.** `knowledge/computations/index.md` says `typescript`
    and describes the pre-rehydration check. `knowledge/log.md` uses the reserved
    exact-date heading.

**Replay.** `just verify-answer <request_id>` fetches the evidence document and
both masked sources, re-derives the leak-check verdict with an _independently
transcribed_ scanner in `clients/python/pgw.py`, and compares every recorded
digest. It deliberately does not import the fleet's own attester: a replay that
did would only prove the fleet agrees with itself.

## Tests

424 unit and integration tests pass, up from 295, and 16 Playwright specs (up from 9). The adversarial cases added:

- extraction prompt injection, and a caller who writes the `<<<INPUT` delimiters
- the `valid-empty` / `invalid` distinction, so "unusable" is never read as "clean"
- Japanese and English name and address spans
- a semantic name leak from a mocked Core, caught by the judge veto with the
  deterministic scanner passing
- literal `⟦…⟧` placeholders in raw input, including a half-open probe
- a body carrying `session_id`
- an inbound `X-Request-ID` that must not become the vault key
- missing, expired and generation-mismatched vault mappings
- an invented token, and a token echoed into the prompt that must not become trusted
- a failed release persisting no body and returning no answer
- withheld categories left masked, and released when explicitly allowed
- log fields dropped rather than masked, and exception messages absent from logs
  and spans
- rate limit, oversized body, and the response-schema contract the UI relies on

The Playwright specs were rewritten to drive the new UI: four separate dimensions,
a blocked-request panel, no approve button, and the masked evidence routes.

## What we deliberately did not do

- **Cloud KMS-signed attestation envelopes.** The review calls them optional. The
  digests plus a replayable command deliver the property that matters — a reader
  can re-derive the verdict — without a key-management story we cannot operate in
  the remaining week.
- **Per-request HMAC-bound tokens.** With one vault per request, the cross-request
  linkage they defend against does not exist. The category prefix stays because it
  is what makes the masked prompt legible in the demo, and its disclosure is now
  documented rather than denied.
- **Authenticated human review.** Out of scope, for the reason given above. It is
  a post-submission item.
- **Making the Synthesis A2A surface execute its advertised skill.** Instead the
  Agent Card was corrected: it now says it acknowledges an exchange, and that leak
  checking, release and OKF assembly run on the HTTP routes. An accurate card is
  better than a hastily-built duplicate path.
- **Hash-chained audit records.** Nice-to-have, and in tension with a TTL policy
  that deletes records.

# Round 2 — response to the re-review

**Reviewed document:** [2026-08-24-codex-re-review.md](2026-08-24-codex-re-review.md)

The re-review scored 62/100 and held the submission gate. Its three P0 findings
were all correct, and two of them were worse than the original review's, because
they were regressions introduced by the fixes: the refusal path we added to stop
a leak was itself persisting the leaked text, and the packaging we tightened made
the attestation digests unusable in exactly the environment that matters.

Every "must pass before submission" item except the two that require a live
deployment is now closed. Items 7 and 8 — one real four-service run and a real
Cloud Trace waterfall — remain open and are blocked on Cloud Run GPU quota, not
on code.

## The three P0 findings

### 1. Refused Core output was persisted verbatim

**Correct, and the most serious thing in the tree.** The refusal helper cleared
only the ephemeral `answer` field. The OKF body was still built from the
unmodified `coreAnswer`, the HTTP layer still persisted `input.core_answer`, and
the unauthenticated evidence routes still served both to anyone holding the
request id. A leak the gate had just refused to release was written to Firestore
under the audit trail's own name.

What changed: on **any** refusal the document body is the literal marker
`content withheld`, and the stored `core_response` is the same marker. Nothing
derived from the rejected text is persisted or served. What survives is the
`attestation` block — the SHA-256 of the rejected response still binds the record
to the exchange, so an auditor holding the original can prove _which_ text the
refusal was about without the store ever having held it.

That last point is the design we chose over the obvious alternative of storing
nothing at all. A refusal is exactly the request an auditor asks about later, and
a record that cannot be tied to an exchange is not evidence. Hashes give the
binding without the content.

Tests: after a refusal, the in-memory record, the Firestore payload, the
`/v1/requests/:id/evidence` route and the `/v1/requests/:id/core-response.md`
route are each asserted to contain neither the rejected Core text nor any mapping
value. One test serialises the entire evidence object and asserts the leaked
string is absent from it, so a future field that starts carrying the body fails
here rather than in production.

### 2. The refusal path rehydrated before deciding

**Correct.** The documented order was "all gates, then rehydrate"; the code ran
the deterministic verdict, the judge, then `rehydrateWithPolicy`, built a result
containing the released string, and only then threw. The string was withheld from
the response, but "no rehydrated text is produced" was false.

The pipeline is now reordered so that is literally true: vault → consistency →
deterministic attester → judge → resolvability → **one** rehydration. Nothing
before the last step reads a mapping value.

The resolvability gate is the part worth explaining. Finding out whether a
placeholder can be resolved used to mean calling the rehydrator and inspecting
`unresolved`. It now consults the mapping's **keys** only
(`unresolvableTokens`), so a request that would have produced dangling
placeholders is refused without any real value ever being assembled into a
string — not even one that is then discarded.

Testing "did not happen" needs a seam, so `synthesize` takes an injectable
`rehydrate`. Asserting on the returned answer cannot distinguish "never
rehydrated" from "rehydrated and then thrown away", and those two states are
precisely what the review found the pipeline confusing. Five tests spy on it:
one per refusal kind, each asserting it was not called, plus one asserting the
success path calls it exactly once.

### 3. Attestation digests were `unavailable` in the production image

**Correct, and it invalidated the OKF feature entirely in production.**
`attestation.ts` hashed a `.ts` source and a `knowledge/` file at runtime and fell
back to the literal string `unavailable`. The Synthesis image ships `dist/`
alone, so neither file is present — and the document was still written with
`verified` and still read back as `machine-confirmed`. Every unit test ran in a
checkout where both files exist, so no unit test could ever have caught it.

Two changes, because either alone leaves a hole:

- **Build-time constants.** `scripts/generate_attestation_digests.mjs` runs as
  part of `pnpm --filter @privacy-gateway/common build` and emits
  `src/attestation_digests.generated.ts`. The digests are compiled into `dist/`,
  so a checkout and a container give the same value. A `--check` mode fails the
  build when the generated file has drifted from the sources it names. Runtime
  hashing is _kept_ where the sources exist and asserted equal to the constant,
  so a stale generated file is a loud `AttestationDigestMismatchError` rather
  than a quietly wrong digest. We chose constants over copying the sources into
  the image because two copies can drift and every consumer would then have to
  decide which is canonical.
- **Fail closed on an unusable digest.** `AttestationBlockSchema` now requires
  `^[0-9a-f]{64}$` for all four digests, and `buildGatewayAnswer` refuses to mark
  a document `stable` or write `verified` when any of them fails that check. The
  document becomes `status: draft` and reads back as `unverified`. The reason is
  stated in the `# Attestation` body rather than dropped, per SPEC §10.5.

Three layers of test, because the failure was specifically one that source-level
tests cannot see:

- unit tests that an `unavailable` digest produces a draft, never machine-confirmed;
- `agents/synthesis/test/dist_attestation.test.ts`, which builds the workspace and
  runs the compiled JavaScript under `node`, asserting a valid digest and a
  `stable` document out of `dist/`;
- `just image-test`, which starts the **real production image** and reads
  `GET /v1/attestation`, failing unless both digests are 64 lowercase hex
  characters.

The build also revealed a genuine packaging bug while we were there: the build
stage never copied `knowledge/`, so the digest generator could not run inside the
image at all. All three Dockerfiles now copy `knowledge/computations/` into the
**build** stage only — the runtime image still ships no bundle, because the
digest is already baked in.

Verified output from the running container:

```

computation_sha256: efa7e03c46f5158efed2641a4988cb7f49a32792a67d563826be070946d6cdbc
```

## The P1 findings

### OKF source URLs dangled, and replay was incomplete

`sources[]` named `/requests/<id>/…` while the gateway served
`/v1/requests/<id>/…`, so following the provenance link as an origin-relative URL
returned 404. Both are now built from one `REQUEST_ARTIFACT_BASE` constant, and a
test asserts it equals the served route.

`pgw.py verify` checked two hashes and a verdict, and merely _printed_
`attester_sha256`. It now checks all four digests plus the request id and the
verdict, rejects any digest that is not 64 lowercase hex characters before
comparing it to anything, and hashes the attester and computation files from the
bundle in the checkout. When the checkout is absent those two are reported as
`SKIP` — never silently as a pass.

The attester's prompt binding was **asserted, not attested**: `verify()` accepted
any non-empty `masked_prompt_hash` without ever seeing the prompt, so a receipt
could name any prompt at all and still pass. The receipt now carries
`masked_prompt` itself and the attester recomputes the hash from it, rejecting a
mismatch. `executor.receipt`, `RECEIPT_FIELDS` and the runner instructions all
moved to the same six-field list, and a test enforces that they agree.

### The logging allowlist was not semantically typed

`enum`, `id` and `hash` accepted any string and truncated it, and
`LeakJudgeSchema.categories` was `z.array(z.string())`. A judge answering
`categories: ["Taro Yamada"]` therefore wrote a real name into the logs _and_ the
public refusal body. Truncation made it worse, not better: it emitted a prefix of
the value instead of dropping it.

Now: `PII_CATEGORIES` is a closed enum of the eleven categories the tokenizer can
allocate, and anything outside it is dropped with a count kept (`dropped_categories`)
so a judge answering in prose is visible in telemetry rather than invisible.
`id` validates UUID or W3C trace/span-id syntax, `hash` validates SHA-256 syntax,
`enum` validates an identifier shape that model output and exception messages both
fail, and a new `token_list` kind accepts only `⟦TYPE_N⟧` placeholders.

The free-text `message` channel is gone. `Logger` no longer has
`info`/`warn`/`error`/`debug` overloads at all — only `event(name, fields,
severity)` — and the message _is_ the event name, checked against the same enum
pattern. A call site can no longer interpolate a value into a log line because
there is nowhere to put one.

Startup config errors log the key and the zod error **code** only. `issue.message`
routinely quotes the input it rejected, and the value of a misconfigured env var
is exactly the kind of thing — a URL carrying a token, a pasted secret — that must
not reach a log at startup.

### Vault semantics

`TokenVault.get()` returns a discriminated `missing | expired | live` rather than
a nullable entry, so the documented `410 vault_expired` path is reachable for the
first time; missing stays 409. `expired` carries the expiry time so the caller can
say when it lapsed without a second read.

The non-transactional Firestore fallback is **removed**, not merely discouraged.
`runTransaction` is now required by the interface, and a client without one raises
rather than silently degrading to a read-modify-write — the path that loses one
caller's mapping under concurrency. The evidence store got its own narrower
interface, since it writes one document per request exactly once and has no
read-modify-write to make atomic.

Evidence `expires_at` is now the vault entry's own expiry, read back from the
document's `stale_after`. Recomputing `now + TTL` at persistence time let the
service serve a record past the freshness the document itself advertises.

### Verification recipes

`just smoke` sent `{"prompt": …}` against a `strict()` schema that accepts only
`{"text": …}`; it was a guaranteed 400. Fixed, along with the same body in
`DEPLOY.md` and `DEPLOY.ja.md`.

`just verify-auth` expected `403` then `200` from a laptop against
internal-ingress services. That result is impossible: ingress is evaluated before
IAM, so a request from outside the VPC is refused at the network edge whether or
not it carries a valid token. The recipe now expects `403` both ways and says so,
and a `200` there would mean the ingress setting had regressed.

The IAM-success half is genuinely unobservable from outside, so it moved to
`just verify-auth-internal`: a Cloud Run **Job**
(`infra/terraform/verify_job.tf`) that attaches to the fleet subnet with Direct
VPC egress and runs as the Gateway's own service account, asserting `200` with an
ID token and `403` anonymously. That is the exact hop the Gateway makes in
production, made by the same identity — borrowing a broader identity would prove
something the fleet does not depend on. A Job costs nothing at rest; it bills only
for the seconds of one execution, which is why it is a Job and not a probe
service. The manual path is documented for a deployment that sets
`enable_verify_job = false`.

### The deadline cancelled nothing

`Promise.race` returned 504 and stopped _waiting_; the Core, Synthesis and Gemma
calls kept running, kept spending model budget and kept persisting evidence long
after the caller had been answered.

There is now one request-scoped `AbortController` per `/v1/ask`. Its signal is
passed through `ask` → Core A2A → Synthesis HTTP → the Gemma judge, and the
timeout aborts it. It is also aborted in `finally`, so anything still in flight
behind an already-sent response is cancelled too.

The Gemma **span extractor** runs through the ADK runner, which offers no
cancellation seam. Rather than pretend otherwise, `ask` checks the signal at every
step boundary (`checkpoint()`), so an extraction that completes after the deadline
cannot cause the work that would follow it. That is an honest partial: the model
call itself finishes, but nothing downstream of it runs.

`authorizedFetch` had two real bugs on this path: a caller-supplied signal that
was _already_ aborted was ignored, because `addEventListener` never fires for an
event that has happened, so an already-cancelled request was sent anyway; and the
listener was never removed, so a request-scoped signal accumulated one listener
per hop. Both fixed, with tests.

## The P2 findings

**`http_client` origin allowlist.** Every non-local https URL was assumed to be a
Google IAM target, so one mistyped `SYNTHESIS_BASE_URL` would have delivered this
fleet's service identity token to whatever host the typo named.
`setIdTokenAudienceAllowlist` is called at each agent's startup with exactly the
origins it talks to, and an origin outside it raises `UnknownAudienceError`
_before_ a token is minted — the credential is never created, not merely not
sent. An empty allowlist means none was declared (`just dev`, tests) and the
previous behaviour holds.

`fetchAgentCard` caught `IdTokenError` and rethrew a generic `Error`, so the
gateway lost the `auth.id_token.failed` classification and reported a credential
fault as a missing card. Both typed auth errors now propagate, and the lookup does
not try the second card path after one — trying `agent.json` cannot fix a
credential problem, it only doubles the latency of a request that will fail.

**Core span concurrency.** The agent held one mutable `modelSpan` while Cloud Run
runs it at concurrency 40, so one request's `afterModelCallback` could end
another's span. The handle is now keyed by the ADK callback context in a
`WeakMap`, and the comment claiming the calls cannot interleave — which was
simply false — is gone. A call that never returns now drops its span with its
context instead of being ended by whichever request starts next.

## Documentation contradictions

Fixed in both languages: the `guard.ts` header no longer claims it structurally
catches an unstructured span Gemma missed (no regex can — it says what it does and
does not cover, and where the residual risk is handled); `core/src/agent.ts` no
longer claims the package graph is the guarantee (IAM is, and the dependency edge
is a convention a future commit can add); the Synthesis `LlmAgent.description`
now matches its Agent Card and claims only acknowledgement; ARCHITECTURE lists the
six-field receipt, the `/v1`-prefixed source paths, the correct `X-Request-ID`
behaviour (ignored, not echoed) and the correct refusal-persistence rules
(including which refusals precede any document at all); DEPLOY says `request_id`

# Round 3 — closing the retry-to-release path

Round 2's "narrow exception" (§3, above) let a `judge_flagged` verdict be reversed:
an unevidenced flag over an attester-clean body was re-asked once, and a clear
second answer released the request. On reflection that is a probabilistic veto
being re-rolled until it stops objecting, which is exactly the shape of "fail
closed" this project otherwise refuses to allow anywhere else in the pipeline.

The exception is gone. The judge's **first** verdict is now authoritative:
`leak: true` always refuses (`judge_flagged`, 422), with no path by which a
second call turns a flag into a release. When that first verdict flags a leak
while naming no category, over a body the deterministic attester already
passed, the judge is still asked once more — but only to enrich the category
list the refusal carries. The second call's `leak` value is discarded outright;
only categories it names, if any, are adopted. The outcome is still a refusal.

`attestation.judge_retries` is kept as a field name, and its cardinality is
unchanged (0 or 1, capped by the pipeline), but its meaning changed from
"verdict re-rolls" to "category-enrichment attempts." It now appears only on
refusals, never on releases — the schema comment, the `judge.retry` log event
documentation, the audit-list JSDoc and the `pgw-client` skill doc were all
updated to say so.

Why not keep the downgrade path: the deterministic attester does not detect
names or postal addresses at all, so an unevidenced flag over an attester-clean
body is exactly the case where the judge is the only coverage those categories
get. Re-asking a probabilistic veto until it clears is how a veto becomes
theatre rather than verification — the same reasoning Round 2 already applied
to the deadline gate ("a cost gate that retries forever becomes the outage it
was meant to prevent") applies here to a disclosure gate. The context/`[masked]`
input redesign from Round 1 (§3, above) is the real fix for the false-positive
rate that motivated the exception in the first place; a second chance at the
verdict was never load-bearing for that fix and is not missed.

## The audit capability travelled in the query string

`/v1/audit` accepted its token as `?key=<token>` as well as an `X-Admin-Token`
header, and the deploy guide handed out `/audit?key=…` as the shareable demo
link. The code comment claimed the query token "is not logged." That was simply
false: Cloud Run writes a request log for every request, and Cloud Logging's
`httpRequest.requestUrl` carries the query string verbatim. Anyone holding Logs
Viewer, a log sink, or an exported URL held the capability to enumerate every
retained evidence document.

Query-parameter authentication is gone. The header is now the only accepted
channel, and a correct token presented as `?key=` answers 404 like any other
non-token — there is a test that pins exactly that, because "we stopped reading
it" and "we refuse it" are different claims and only the second is checkable.

The shareable link survives as `/audit#key=<token>`. A fragment is never
transmitted to the server, so the token reaches the page without reaching the
request log at all; the page consumes it once, moves it to `sessionStorage`,
strips the fragment so it does not persist in history or in a later referrer,
and thereafter sends it only as the header. A Playwright spec asserts the
fragment is cleared and that the token appears in no request URL.

**The deployed token was rotated**, because the old one had been used in `?key=`
URLs against a live revision and must be treated as already disclosed.

## The kill switch treated "no maximum" as "maximum zero"

`scaleToZero` wrote `template.scaling.maxInstanceCount = 0` and then accepted an
_absent_ `maxInstanceCount` on read-back as proof the GPU was capped. Both halves
were wrong. Cloud Run's maximum instance count starts at 1, and
`RevisionScaling.maxInstanceCount` is a plain proto3 `int32` with no presence
tracking — a 0 is never serialised, so the server received an absent field, which
means _no maximum_: the limit was removed rather than set to zero. The success
check then read that same absent field back and called it a capped GPU. The
switch reported a stopped fleet while nothing had stopped it, and the live-fire
proof drew the opposite conclusion from the state it was shown.

The switch now uses Cloud Run **manual scaling** — `scaling.scalingMode = MANUAL`
with `scaling.manualInstanceCount = 0` — which is the documented mechanism for
holding a service at zero instances. `ServiceScaling.manualInstanceCount` is the
one field there declared `proto3_optional`, so an explicit 0 is presence-tracked
and survives the round trip; that is what makes zero expressible at all.
`template.scaling.maxInstanceCount` is now deliberately left alone.

Two further changes follow from the same principle. The switch additionally
revokes the gateway's and synthesis's `run.invoker` on `gemma-serving`, as belt
and braces: manual scaling is what stops the GPU, and this makes sure that even a
Cloud Run that somehow admitted a request would have nobody authorised to make
it. And success is now decided by reading the applied state back **explicitly**,
as a scaling mode _and_ a count — an absent or empty scaling block now fails with
`scale_to_zero_not_applied` rather than passing. Nothing is inferred from a field
the server did not send, which was the whole defect.

`just restore-after-kill` had to learn the new mechanism too: `cloudrun.tf` now
declares `gemma-serving`'s service-level `scaling { scaling_mode = "AUTOMATIC" }`
so Terraform owns the field and an apply actually puts it back. Without that
block Terraform would see no diff and leave the GPU pinned off after a restore.

**Fired live on 2026-08-30 against production.** All three mutations landed
within two seconds on a single delivery, with no retry loop and an empty
dead-letter queue. The Admin API then reported
`scaling: {"scalingMode":"MANUAL","manualInstanceCount":0}` — an explicit zero,
present in the response — and Cloud Run logged
`Shutting down user disabled instance` for `gemma-serving` nine seconds later.
That last line is the thing the old mechanism never produced. The fleet was
restored, the marker cleared, and `just smoke` passes again.

Firing it also surfaced a second, quieter defect: `just restore-after-kill`
cleared the tripped marker with `gcloud run services update
--remove-annotations`, a flag that does not exist, behind a
`|| echo "(no marker was set)"`. The failure printed a message asserting the
opposite of what had happened and left the marker set — and a marker left set
makes every later trip a no-op, so the switch was silently disarmed. It now
clears the annotation by read-modify-write through the Admin API and reads back
to confirm, failing loudly if the marker survives.
