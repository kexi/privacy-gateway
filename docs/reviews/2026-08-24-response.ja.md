# 設計レビューへの回答（要約）

**英語版（正）:** [2026-08-24-response.md](2026-08-24-response.md)

このファイルは要約である。判断の根拠と「やらなかったこと」の理由は英語版に書いてあるので、
細部が必要ならそちらを読むこと。

## 第 1 ラウンド

最初のレビューの中心的な指摘は正しかった。プライバシー保証が **fail open** していた —
Gemma が使えないとき氏名・住所が素通りし、リークチェックの失敗がリリースを止めず、
呼び出し元が制御できるプレースホルダが再水和オラクルになり、再水和済み PII が
TTL 保護外に無期限で永続化されていた。いずれも塞いだ。

支配的な判断は **スコープを削ってから fail closed にする** こと。セッションを廃止し、
1 リクエスト = サーバ生成の `request_id`（UUIDv7）= Vault キー 1 件にした。これだけで
クロスセッションのオラクル、並行性競合、期限切れ再スタートの衝突、マルチターン連結の
リスクが同時に消える。ターンをまたぐプレースホルダの安定性は失われるが、提出物としては
正しいトレードだと判断した。

## 第 2 ラウンド — 再レビューへの回答

再レビューは 62/100 で提出ゲートを **HOLD** とした。P0 が 3 件あり、いずれも正しい。
そのうち 2 件は前回の修正が生んだ **リグレッション** で、元の指摘より質が悪い。
リークを止めるために追加した拒否パスがリークしたテキストそのものを永続化しており、
締めたパッケージングが「まさに問題になる環境」で attestation ダイジェストを
使い物にならなくしていた。

ライブデプロイを要する 2 件を除き、"must pass before submission" は全て closed。

### P0 1 — 拒否された Core 出力を逐語的に永続化していた

**指摘は正しく、ツリー中で最も深刻だった。** 拒否ヘルパは一時的な `answer` しか消して
おらず、OKF 本文は無修正の `coreAnswer` から組み立てられ、HTTP 層は `input.core_answer` を
そのまま永続化し、**認証のない** evidence ルートが request id を知る者に両方を返していた。
ゲートがリリースを拒否したはずのリークが、監査証跡自身の名前で Firestore に書かれていた。

**変更:** あらゆる拒否で、ドキュメント本文は `content withheld` というマーカーになり、
保存される `core_response` も同じマーカーになる。拒否されたテキストに由来するものは
一切保存も配信もしない。残るのは `attestation` ブロックで、拒否されたレスポンスの
SHA-256 が引き続きレコードをその交換に **束縛** する。原本を持つ監査人は、ストアが
そのテキストを一度も保持しないまま「どのテキストの話か」を証明できる。

「何も保存しない」を選ばなかった理由はここにある。拒否こそ後から監査人が尋ねる
リクエストであり、交換に紐付けられない記録は証拠ではない。ハッシュが中身なしで
束縛を与える。

**テスト:** 拒否後、インメモリのレコード、Firestore のペイロード、
`/v1/requests/:id/evidence`、`/v1/requests/:id/core-response.md` のいずれにも、
拒否された Core テキストもマッピング値も含まれないことを検証する。うち 1 件は
evidence オブジェクト全体を JSON 化して該当文字列の不在を主張しており、将来
本文を運び始めるフィールドが増えても本番ではなくここで落ちる。

### P0 2 — 拒否パスが判断前に再水和していた

**指摘は正しい。** ドキュメント上の順序は「全ゲート → 再水和」だったが、実際のコードは
決定的判定 → judge → `rehydrateWithPolicy` → リリース文字列を含む結果を構築 → throw
だった。文字列はレスポンスから外されていたが、「再水和済みテキストは生成されない」は
偽だった。

順序を組み替え、これが文字通り真になった: Vault → 整合性 → 決定的 attester → judge →
解決可能性 → **1 回だけ** の再水和。最後のステップより前でマッピングの値を読む箇所はない。

**解決可能性ゲート**が要点。プレースホルダが解決できるかを知るのに、以前は再水和器を
呼んで `unresolved` を見ていた。現在はマッピングの **キーだけ** を参照する
（`unresolvableTokens`）ので、宙に浮いたプレースホルダを生むはずだったリクエストは、
実値が一度も文字列に組み立てられないまま拒否される — 後で捨てる文字列すら作らない。

「起きなかったこと」のテストには seam が要るので、`synthesize` は `rehydrate` を
注入可能にした。返ってきた answer を見るだけでは「一度も再水和していない」と
「再水和して捨てた」が区別できず、その 2 状態こそレビューが混同を指摘した当のものだから。
拒否種別ごとに 5 件のスパイテストが「呼ばれていない」ことを、成功パスの 1 件が
「ちょうど 1 回呼ばれる」ことを主張する。

### P0 3 — 本番イメージで attestation ダイジェストが `unavailable` になっていた

**指摘は正しく、本番における OKF 機能を丸ごと無効化していた。** `attestation.ts` は
実行時に `.ts` ソースと `knowledge/` のファイルをハッシュし、失敗すると文字列
`unavailable` にフォールバックしていた。Synthesis イメージは `dist/` しか同梱しないので
どちらも存在しない — にもかかわらずドキュメントには `verified` が書かれ、
`machine-confirmed` として読み戻されていた。ユニットテストは全て両ファイルが存在する
チェックアウト上で走るので、**原理的に検出できなかった**。

片方だけでは穴が残るので 2 つ変更した:

- **ビルド時定数。** `scripts/generate_attestation_digests.mjs` が
  `pnpm --filter @privacy-gateway/common build` の一部として走り、
  `src/attestation_digests.generated.ts` を生成する。ダイジェストは `dist/` に
  コンパイルされるので、チェックアウトとコンテナで同じ値になる。`--check` モードは
  生成ファイルがソースから乖離していればビルドを落とす。ソースが存在する場所では
  実行時ハッシュも **残し**、定数との一致を検証する。乖離した生成ファイルは静かに
  誤ったダイジェストを配るのではなく `AttestationDigestMismatchError` として落ちる。
  ソースをイメージにコピーする案を採らなかったのは、2 つのコピーは乖離しうるうえ、
  どちらが正典かを全ての利用者が判断する羽目になるため。
- **使えないダイジェストでは fail closed。** `AttestationBlockSchema` は 4 つの
  ダイジェスト全てに `^[0-9a-f]{64}$` を要求し、`buildGatewayAnswer` はどれか 1 つでも
  この検査に落ちたら `stable` にせず `verified` も書かない。ドキュメントは
  `status: draft` になり `unverified` として読み戻される。理由は SPEC §10.5 に従い
  `# Attestation` 本文に残し、握り潰さない。

ソースレベルのテストでは見えない種類の障害なので、テストも 3 層にした:

- `unavailable` なダイジェストが draft を生み machine-confirmed にならないユニットテスト
- `agents/synthesis/test/dist_attestation.test.ts` — ワークスペースをビルドし、
  コンパイル済み JavaScript を `node` で実行して、`dist/` から有効なダイジェストと
  `stable` なドキュメントが出ることを検証する
- `just image-test` — **本番イメージそのもの** を起動して `GET /v1/attestation` を読み、
  両ダイジェストが 64 桁の小文字 16 進でなければ失敗する

この作業中に本物のパッケージングバグも判明した。ビルドステージが `knowledge/` を
コピーしていなかったため、イメージ内でダイジェスト生成器がそもそも動かなかった。
3 つの Dockerfile は `knowledge/computations/` を **ビルドステージにのみ** コピーする。
ランタイムイメージは引き続きバンドルを同梱しない（ダイジェストは既に焼き込み済み）。

稼働中コンテナからの実測値:

```
attester_sha256:    8b427a667e6426be7061777d8c7952e57a816b8fbcd0410fdafea2e737529ce9
computation_sha256: efa7e03c46f5158efed2641a4988cb7f49a32792a67d563826be070946d6cdbc
```

### P1 — OKF ソース URL のリンク切れとリプレイの不完全さ

`sources[]` は `/requests/<id>/…` を名乗る一方、Gateway が配信するのは
`/v1/requests/<id>/…` だったので、来歴リンクを origin 相対 URL として辿ると 404 だった。
両者を `REQUEST_ARTIFACT_BASE` 定数 1 つから組み立て、配信ルートと一致することを
テストで固定した。

`pgw.py verify` はハッシュ 2 つと verdict しか見ておらず、`attester_sha256` は
**表示していただけ** だった。現在は 4 つのダイジェスト全てに加えて request_id と
verdict を検証し、64 桁小文字 16 進でないダイジェストは比較する前に落とし、
attester と computation はチェックアウト内のバンドルファイルからハッシュする。
チェックアウトが無い場合は `SKIP` と明示する — 決して黙って pass にしない。

attester のプロンプト束縛は **主張されていただけで、attest されていなかった**。
`verify()` はプロンプトを一度も見ずに空でない `masked_prompt_hash` を受け入れていたので、
receipt は任意のプロンプトを名乗って通過できた。現在は receipt が `masked_prompt` 本体を
運び、attester がそこからハッシュを再計算して不一致を拒否する。`executor.receipt`、
`RECEIPT_FIELDS`、runner 手順は同じ 6 フィールドのリストに揃え、一致をテストで強制する。

### P1 — ログの allowlist が意味的に型付けされていなかった

`enum` / `id` / `hash` は任意の文字列を受けて切り詰めるだけで、
`LeakJudgeSchema.categories` は `z.array(z.string())` だった。judge が
`categories: ["Taro Yamada"]` と答えれば、実在の氏名がログ **と** 公開拒否ボディの
両方に書かれた。切り詰めは事態を悪化させこそすれ改善しない — 値を落とさず
接頭辞を出力するのだから。

現在: `PII_CATEGORIES` はトークナイザが割り当てうる 11 カテゴリの閉じた列挙で、
範囲外は捨てたうえで件数を保持する（`dropped_categories`）。judge が散文で答え始めた
ことがテレメトリから見えるようにするため。`id` は UUID または W3C trace/span id の
構文を、`hash` は SHA-256 の構文を検証し、`enum` はモデル出力も例外メッセージも
落ちる識別子形状を要求する。`⟦TYPE_N⟧` のみを受ける `token_list` 種別も追加した。

自由文の `message` チャネルは廃止した。`Logger` から `info`/`warn`/`error`/`debug` を
**削除** し、`event(name, fields, severity)` だけを残した。message は event 名そのもので、
他フィールドと同じ enum パターンで検査される。値を差し込む場所が無いので、呼び出し側は
もはやログ行に値を補間できない。

起動時の設定エラーはキーと zod の **エラーコード** のみをログに出す。`issue.message` は
拒否した入力を引用しがちで、設定を誤った環境変数の値こそ — トークン付き URL、
貼り付けた秘密 — 起動時のログに載ってはならない類のものだから。

### P1 — Vault のセマンティクス

`TokenVault.get()` は nullable なエントリではなく `missing | expired | live` の
判別共用体を返す。これで文書化されていた `410 vault_expired` が初めて到達可能になった
（missing は 409 のまま）。`expired` は失効時刻を持つので、呼び出し側は再読み込みなしに
「いつ切れたか」を言える。

トランザクションなしの Firestore フォールバックは **非推奨ではなく削除** した。
`runTransaction` はインタフェース上必須になり、それを持たないクライアントは
read-modify-write に黙って劣化するのではなく例外を投げる — 並行時に一方の呼び出し元の
マッピングを失うのがまさにその経路だから。evidence ストアには専用のより狭い
インタフェースを与えた。1 リクエスト 1 ドキュメントをちょうど一度書くだけで、
アトミックにすべき read-modify-write が存在しないため。

evidence の `expires_at` は Vault エントリ自身の失効時刻を、ドキュメントの
`stale_after` から読み戻して使う。永続化時に `now + TTL` を計算し直す実装は、
ドキュメント自身が主張する鮮度を過ぎたレコードを配信させていた。

### P1 — 検証レシピ

`just smoke` は `{"text": …}` しか受けない `strict()` スキーマに対して
`{"prompt": …}` を送っており、確実に 400 だった。`DEPLOY.md` / `DEPLOY.ja.md` の
同じボディも含めて修正。

`just verify-auth` はラップトップから internal ingress のサービスに対して
`403` → `200` を期待していた。これは **原理的に不可能** な結果で、ingress は IAM より
先に評価されるため、VPC 外からのリクエストは有効なトークンの有無にかかわらず
ネットワーク端で拒否される。現在は両方 `403` を期待し、その旨を明記した。
ここで `200` が返れば ingress 設定がデグレしたということになる。

IAM が **受理する** 側の証明は外からは本当に観測できないので、
`just verify-auth-internal` に分離した。Cloud Run **Job**
（`infra/terraform/verify_job.tf`）がフリートのサブネットに Direct VPC egress で接続し、
Gateway 自身のサービスアカウントで走り、ID トークン付きで `200`、匿名で `403` を主張する。
これは Gateway が本番で行うのと同一のホップを同一の ID で行うもの — より広い権限の ID を
借りれば、フリートが依存していない何かを証明することになる。Job は待機中の課金がなく、
1 回の実行の秒数だけ課金されるので、常駐プローブサービスではなく Job にした。
`enable_verify_job = false` のデプロイ向けに手動手順も文書化してある。

### P1 — デッドラインが何もキャンセルしていなかった

`Promise.race` は 504 を返して **待つのをやめる** だけで、Core / Synthesis / Gemma への
呼び出しは走り続け、モデル予算を使い続け、呼び出し元が応答を受け取った後も evidence を
書き続けていた。

現在は `/v1/ask` ごとに request スコープの `AbortController` が 1 つある。その signal は
`ask` → Core A2A → Synthesis HTTP → Gemma judge へ渡され、タイムアウトがそれを abort する。
`finally` でも abort するので、応答送信済みの背後で飛んでいるものもキャンセルされる。

Gemma の **スパン抽出** は ADK ランナー経由で、キャンセルの seam が無い。そこを取り繕わず、
`ask` は各ステップ境界で signal を確認する（`checkpoint()`）。デッドライン後に完了した
抽出が、その後に続くはずだった処理を引き起こせないようにするため。これは正直な部分解で、
モデル呼び出し自体は完走するが、その下流は何も走らない。

`authorizedFetch` にはこの経路で実バグが 2 件あった。呼び出し元の signal が **既に**
abort 済みの場合、`addEventListener` は既に起きたイベントには発火しないので無視され、
キャンセル済みのリクエストが送られていた。またリスナが除去されず、request スコープの
signal はホップごとにリスナを蓄積していた。両方ともテスト付きで修正。

### P2

**`http_client` の origin allowlist。** ローカル以外の https URL は全て Google IAM の
ターゲットとみなされていたので、`SYNTHESIS_BASE_URL` の打ち間違い 1 つで、このフリートの
サービス ID トークンが打ち間違いの指すホストに届いていた。`setIdTokenAudienceAllowlist` を
各エージェントの起動時に、そのエージェントが話す相手の origin だけで呼ぶ。範囲外の origin は
トークンを鋳造する **前に** `UnknownAudienceError` を投げる — 資格情報は送られないのではなく
そもそも作られない。allowlist が空なら未宣言（`just dev`、テスト）とみなし従来の挙動を保つ。

`fetchAgentCard` は `IdTokenError` を捕まえて汎用 `Error` に詰め替えていたので、Gateway は
`auth.id_token.failed` の分類を失い、資格情報の障害を「カードが見つからない」として報告して
いた。型付き認証エラーは両方そのまま伝播し、発生後に 2 つ目のカードパスを試さないようにした
— `agent.json` を試しても資格情報の問題は直らず、どのみち失敗するリクエストの遅延が
倍になるだけだから。

**Core のスパン並行性。** エージェントは可変の `modelSpan` を 1 つ保持していたが、
Cloud Run は同時実行 40 で走らせるので、あるリクエストの `afterModelCallback` が別の
リクエストのスパンを終了させうる。ハンドルは ADK のコールバックコンテキストをキーとする
`WeakMap` に移し、「呼び出しはインターリーブしえない」という **端的に偽だった** コメントを
削除した。戻ってこない呼び出しのスパンは、次に始まったリクエストに終了させられるのではなく、
コンテキストとともに落ちる。

### ドキュメントの矛盾

両言語で修正した。`guard.ts` のヘッダは「Gemma が見落とした非構造スパンを構造的に捕捉する」
という主張をやめ、何を覆い何を覆わないか、残余リスクがどこで扱われるかを述べる。
`core/src/agent.ts` は「パッケージグラフが保証」という主張をやめた（保証は IAM であり、
依存エッジは将来のコミットが追加しうる規約に過ぎない）。Synthesis の
`LlmAgent.description` は Agent Card と一致し、acknowledge のみを主張する。
ARCHITECTURE は 6 フィールドの receipt、`/v1` 付きのソースパス、正しい `X-Request-ID`
挙動（エコーではなく無視）、正しい拒否永続化ルール（どの拒否がドキュメント生成より前かを含む）
を記載する。DEPLOY は `session_id` ではなく `request_id` と言う。Gateway は Synthesis の
拒否をフリート唯一残っていた手書きキャストではなく `ReleaseRefusalSchema` でパースする。

UI のバッジは **`machine-confirmed: leak-policy only`** になった。tier 値自体は
SPEC §5.3 の用語なので逐語で残すが、"machine-confirmed" 単体は回答全体についての主張に
読めてしまう。実際に確認したのは「トークン化された core レスポンスがそれ自身の生の
識別子を漏らしていない」ことだけである。

## 残っている項目

提出ゲートの **7 番と 8 番** — 実 4 サービスの稼働 1 回と、Core に Firestore IAM が
無いことを含む実 Cloud Trace のウォーターフォール — は未了。ライブデプロイが必要で、
`gemma-serving` 向けの Cloud Run GPU（Nvidia L4）クォータ待ちである。コード側の障害は無い。
`just verify-auth`、`just verify-auth-internal`、`just smoke`、`just verify-answer` は
クォータが下り次第そのまま証跡を出せる状態にある。

それまでの正直な言い方は、再レビューが求めたとおりのものだ:
**このフリートはプロセス内とコンテナ内で証明済みであり、本番では未証明である。**
