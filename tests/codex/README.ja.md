# Codex CLI エンドツーエンドシナリオ

第三者製のエージェント CLI が、無改造のままこの fleet をモデルとして選べることの証明。
[`pitty`](https://github.com/kexi/pitty) が本物の擬似端末 (PTY) の中で `codex exec`
を走らせ、ストリーミング出力を検証する。

> **どちらを実行するか。** 日常の検証は **`just codex-smoke`** のみを実行する。
> フル版の **`just codex-e2e`** は**提出前・リリース前の最終チェック**に限る —
> 実 CLI を動かすため、ターン開始前に約 147 KB の指示文を単一 GPU でマスクし
> きる必要があるからである。

```sh
just codex-smoke                            # 日常: 小さなペイロードでワイヤ契約を検証
just codex-e2e                              # 最終チェック: 実 CLI シナリオ 2 本
just codex-e2e tests/codex/pgw-smoke.yaml   # 単体
```

| シナリオ             | レシピ        | 保証する内容                                                                                                                                                                                  |
| -------------------- | ------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `pgw-responses.yaml` | `codex-smoke` | Codex が依拠する Responses API の契約。SSE ストリームが `response.created` で始まり、実行ごとの nonce を含み、`response.completed` で終端する。CLI を使わないので 147 KB のプロンプトも無い。 |
| `pgw-smoke.yaml`     | `codex-e2e`   | Codex が Responses API 経由で fleet に到達し、回答を出力して 0 で終了する。                                                                                                                   |
| `pgw-masking.yaml`   | `codex-e2e`   | メールアドレスを含むプロンプトが往復する。実行ごとの nonce とアドレスの両方が返るので、マスキングと再水和がクライアントから透過的であることが分かる。                                         |

## ヘビー経路と、その既知の限界

`codex-e2e` はプロトコルのテストであると同時に**負荷**のテストでもある。Codex CLI は
毎ターン、自身の指示ブロック（ツールスキーマ、ワークスペース規約、ポリシー文など
およそ **147 KB**）を先頭に付ける。そのすべてを、外部へ送る前に非構造 PII について
走査しなければならない。デプロイ時のチャンクサイズ 4 KB では Gemma 呼び出し約 37 回
となり、これを単一 GPU の llama.cpp スロット 4 本にファンアウトするため、**コールド
状態での最初の CLI ターンは 150 秒のリクエスト期限を超えうる**。これは単一 GPU 構成の
既知のキャパシティ限界であって fleet のロジックの欠陥ではない: ゲートウェイは応答する
か明示的に拒否するかのどちらかであり、速度のためにマスキングを緩めることは決してない。

2 回目以降が大幅に安くなる理由は 2 つある。ゲートウェイは抽出済みチャンクをプロセス内
LRU に保持しており、CLI のプリアンブルはターン間でバイト単位に同一なので、ウォームな
インスタンスは変化した分だけを再抽出する。事前に `just warm` を打てばモデルロードの
時間も外せる。タイムアウトした場合、プロトコル自体が生きているかを判定するのは
`just codex-smoke` である。

日常用シナリオを分けたのは、両者を束ねると「ワイヤ形式の退行」と「GPU の
キャパシティ限界」が同じ赤として現れてしまうからである。

## 前提条件

- **`~/.codex/pgw.config.toml`** — `wire_api = "responses"` で `pgw` プロバイダを宣言する
  (Codex 0.149 以降は `wire_api = "chat"` を拒否し、`config.toml` 内の `[profiles.*]`
  も拒否するため、別ファイルにしている)。詳細は `skills/pgw-client/CLIENT.md` の
  Codex 節を参照。
- **ログイン済みの `codex` CLI**。シナリオは `PATH` 上のバイナリを spawn する。
  ターン自体は gateway が処理するが、Codex の起動には Codex 自身の資格情報が要る。
- **到達可能な gateway** (そのプロファイルの `base_url`)。

## なぜ PTY か

`codex exec` は端末に接続されているかどうかで、ステータス行の描画や最終回答の
フラッシュの仕方を変える。stdout をパイプすると人間が見るのとは違うバイト列を
検証することになるため、pitty は本物の PTY を確保する。

## なぜ CI に入れないか

これらのシナリオは**本番の** fleet を叩く。実行のたびに GPU 付き Cloud Run
インスタンスが起動し、アイドルアウトするまで (最終リクエストから約 15 分) 課金される。
コールドスタートではマスキング処理が始まる前に約 2 分かかるため、タイムアウトを
240 秒にしてある。これを push ごとに回すのは、モック済みのスイートが既にカバー
している内容を実費で再証明するだけになる (`pnpm -r test` がマスキングとゲートの
ロジックを、`just web-e2e` が Core と Gemma を HTTP でモックしたブラウザ経路を
カバーしている)。これは意図的に手動のままにしている唯一のテストで、その理由は
モックできない唯一のテストだから — 鎖のどこにも代役がいないことこそが価値である。

## これらのシナリオが踏んだ 2 つの罠

**`expect` は変数を展開しない。** pitty v1.2.2 は `spawn` と `send` の中では
`${VAR}` を展開するが、`expect` ブロックの中では**展開しない**。つまり
`contains: 'ACK ${PGW_NONCE}'` と書くと、その文字列そのものと比較されるため
決して一致しない。そこで `pgw-responses.yaml` は固定の接頭辞
(`"text":"ACK PGW`) を検証し、nonce は*リクエスト側*に埋め込む — nonce が効くのは
そちらであり、キャッシュされた回答や捏造した回答では、この実行のプロンプトに対する
応答を作れない。`pgw-masking.yaml` も同じ形なので、その nonce 検証は見た目より弱い。

**nonce が PII に見えてはいけない。** 以前の nonce は `PGW-$(date +%s)-$RANDOM`
だった。この長い数字の並びはカード番号そのものに見えるため、トークナイザが
`CREDIT_CARD` として検出してマスクし、`CREDIT_CARD` は withheld カテゴリなので
再水和もされなかった。fleet は設計どおりに振る舞っていたのに、シナリオだけが
失敗していたことになる。現在の nonce は英大文字のみである。

## masking シナリオが証明しないこと

アドレスが返ってくることは検証するが、それは再水和が返すべきものだからである。
アドレスが**転送中に**マスクされていたかどうかは見えない。その証拠は gateway
側にある。`/v1/requests/<request_id>` がマスク済みプロンプトを保持しており、
`just verify-answer <request_id>` が attestation のダイジェストを再検証する。
